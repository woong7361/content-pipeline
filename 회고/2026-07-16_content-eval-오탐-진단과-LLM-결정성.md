# 2026-07-16 · content-pipeline eval 오탐 진단과 LLM의 결정성

> 발단: "runs에 추가된 애들 보면 eval이 계속 낮아지는 것 같다"
> 결론: 점수는 낮아진 게 아니었고, 낮은 점수의 실체는 **우리가 저작한 오탐**이었다.

## 1. 관찰과 실제

점수는 하락하지 않았다. 평평하거나 진동했다.

| iter | ch8c0716 | ch8c0717 |
|---|---|---|
| 001 | 3.06 | 2.64 |
| 002 | 2.64 | 3.38 |
| 003 | 2.88 | 2.42 |
| 004 | 2.88 | 2.24 |
| 005 | 2.88 | **3.66** |

ch8c0716은 2.88에 못 박혔고, ch8c0717은 진동하다 마지막이 제일 높았다. "하락"보다 나쁜 신호였다 — **루프가 점수에 아무 영향을 못 주고 있었다.**

## 2. 진단 체인

### (1) content_refine이 한 번도 실행되지 않았다

```python
if asset_change_needed:        # 1순위
elif design_status != "PASS":  # 2순위 → design_refine
else:                          # 3순위 → content_refine
```

design_review가 10/10 iteration 전부 REJECT였으므로 content_refine은 **0회** 실행됐다. HTML을 고친 stage는 10/10 전부 design_refine이었고, design_refine의 프롬프트엔 content_critique가 없다.

그 결과 content_critique는 매 iteration 무거운 모델 호출로 생성·저장되지만 **아무도 읽지 않았다.** 증거는 critique의 `priority_issues`가 iter 001~005 내내 같은 5개를 반복한 것이다 — 제출 잠금 없음, 9차시 CTA가 hash만 변경, 피드백 결과 통보형, 복구 장면 순서, 유형 C 자동 채점 누락. 다섯 번 지적됐고 다섯 번 다 버려졌다.

### (2) eval의 "누락"은 대부분 오탐이었다

ch8c0716의 content_fidelity=1을 뒷받침하던 6건을 전수 검증한 결과 **6건 전부 오탐**이었다.

- `channel=question_display` ×3 — 문항이 아니라 **storyboard의 예시 화면 문구**. 같은 section에 `questions[]`로 실제 문항 4개가 있고 builder가 원문대로 렌더했다. 예시를 화면에 넣으라는 건 **5번째 가짜 문항을 만들라는 뜻**이다.
- `channel=interaction_instruction` ×3 — "3개의 시계 중 하나를 직접 터치하여 선택." 같은 **조작 방법 제작 지시**.

반면 실제 원문 보존율은 만점에 가까웠다: `questions[].prompt`+`choices` **38/38**, `dialogue` **14/14**, `cta` **5/5**.

### (3) 근원 — planner가 `예:` 마커를 버렸다

storyboard 원문:

```
| 2 | 문제 표시 (전광판) | • 화면 중앙 상단의 대형 전광판에 문제 텍스트 출력.
                        • 예: 전광판에 `[8시 15분 전]`이라고 적혀 있어요... |
```

planner 출력:

```json
{ "channel": "question_display",
  "content": "전광판에 `[8시 15분 전]`이라고 적혀 있어요..." }   ← "예:" 증발
```

**예시라는 표시가 planner 단계에서 사라졌다.** 남은 정보만 보면 eval이 필수 노출 문구로 읽는 게 맞다.

### (4) 오탐은 프롬프트에 저작돼 있었다

`content_eval_system.md:21`:

> `sections[].elements[].content`(대사·버튼/전환 라벨·타이틀·완료/보상 텍스트)를 **필수 체크리스트로 삼아**

괄호 안은 7종을 나열하는데 실제 `elements[]`엔 **채널이 19종**이고 나머지 12종은 제작 지시다. **괄호가 데이터와 안 맞는데 지시는 전체를 체크하라고 했다.** eval은 오작동한 게 아니라 지시를 정확히 따랐다.

덧붙여 프롬프트 41행은 *"storyboard의 장면 순서, 핵심 사건이 보존되는지 봅니다"*라고 하는데, **eval에게 storyboard를 주지 않는다.** `input.json`엔 `md_path` 경로 문자열만 있다. eval 산출물 10개 중 storyboard를 언급한 것은 0개였다.

### (5) 게이트가 만족 불가능했다

`min_axis: content_fidelity = 5.0` = 누락 0개 = 만점 요구. 73개 element 중 ~50개가 설계상 HTML에 없는 제작 지시인데, judge가 그걸 **하나도 빠짐없이 정확히 제외해야만** 5점이다. **어떤 산출물도 PASS할 수 없었다.**

## 3. LLM의 결정적인 것과 비결정적인 것

오늘의 핵심 발견. 같은 입력(`2학년_8차시(시간)_임상현.md`)으로 planner를 여러 번 돌려 측정했다.

### 안정적인 것

| | 7/15원본 | v1 | v2 | 0717 | probeA | probeB |
|---|---|---|---|---|---|---|
| `sections` | 12 | 12 | 12 | 12 | 12 | 12 |
| **`questions`** | **14** | **14** | **14** | **14** | **14** | **14** |
| **`choices`** | **24** | **24** | **24** | **24** | — | — |

### 흔들리는 것

| | 7/15원본 | v1 | v2 | 0717 |
|---|---|---|---|---|
| `elements` | 73 | 58 | **101** | 87 |
| `channel` 종류 | 19 | 13 | 14 | 17 |
| `dialogue` | 14 | **9** | 15 | 15 |
| `cta` | 5 | **9** | **10** | 6 |

### 왜 갈리는가

**`questions`가 안정적인 이유는 "typed slot이라서"가 아니다.** 문서가 명시적으로 열거하기 때문이다:

```
- 문제 1: ... 보기: 2시 55분 시계(정답) / 3시 5분 시계 / 3시 55분 시계
- 문제 2: ... 보기: 11시 10분 전 / 12시 10분 전(정답) / ...
```

번호가 매겨져 있고, 프롬프트도 "문제가 12개면 `questions`도 12개"라고 개수를 못 박는다. LLM은 **이미 세어진 목록을 옮기기만** 한다.

대사는 표 셀 안에 `<br>`로 이어 붙어 있고, 따옴표 26개 중 무엇이 대사고 무엇이 효과음(`"띠리링~딩동댕!"`)이고 피드백(`"딩동댕!"`)인지 **문서가 안 알려준다.** 경계를 LLM이 정해야 하고, 정하면 흔들린다.

> **원칙: 문서가 세어준 것은 안정적이고, LLM이 경계를 정해야 하는 것은 흔들린다.**
> 이 안정성은 슬롯 설계로 전이되지 않는다. `dialogue`는 가장 명확한 범주인데도 9~15로 흔들렸다.

### 그런데 드리프트가 항상 해로운 건 아니다

최종 검증에서 두 planner의 체크리스트 크기가 **40 vs 47**로 갈렸다. 그런데 **점수는 둘 다 3점으로 동일**했다. 갈린 항목(키패드 숫자 `0`~`9`, `오전`/`오후`, 인증서 제목)이 전부 HTML에 실재해 누락으로 안 잡혔기 때문이다.

> **안정성은 목적이 아니라 수단이다.** 흔들려도 결론에 영향이 없으면 괜찮다. 측정해야 알 수 있다.

### 도구 사용 — LLM은 grep을 쓸 수 있다

"LLM은 못 센다"는 부정확하다. 정확히는 **"눈으로는 못 센다"**이고, codex는 shell 권한이 있다. 문제는 **어떤 grep을 짜느냐**다.

| 명령 | 결과 | 판정 |
|---|---|---|
| `grep -c "[확인하기]"` | **62** | "있네" → **진짜 버그를 놓침** |
| `grep -cF "[확인하기]"` | **0** | "누락" → 정확 |

`-F` 하나 차이다. 대괄호가 **정규식 문자클래스**로 해석돼 "확/인/하/기 중 아무 글자"를 62곳에서 찾는다. 그리고 이게 하필 **거짓 음성** 방향으로 틀린다 — 없는 걸 있다고 하니 아무도 못 잡는다.

## 4. 트레이드오프

### 프롬프트 vs 스크립트

| | 장점 | 치명적 약점 |
|---|---|---|
| **프롬프트 규칙** | 양식 변화에 유연 | 드리프트. **1회 실행으로 효과 측정 불가** |
| **스크립트 추출** | 결정적, 테스트 가능 | **입력 양식에 결합** |

스크립트 결합도는 실측으로 확인됐다. 같은 저자의 다른 기획서(`콘텐츠 기획_SB_임상현.md`)를 대조하니:

| 마커 | 8차시 | 기획_SB |
|---|---|---|
| `버튼 텍스트:` 표지 | 2 | **0** |
| `[대괄호]` 문구 | 47 | 16 |

기획_SB의 대괄호는 `[2수01-03]`(교육과정 코드), `[활동 1 예시 화면]`(**마크다운 이미지 alt**), `[6420]`(문제 숫자), `[]`(빈칸)에 다 쓰인다. **8차시에서 통한 추출 규칙이 여기선 교육과정 코드와 이미지 alt를 노출 문구로 뽑는다.**

차이는 **깨지는 방식**이다. 스크립트는 **시끄럽게** 깨지고(새 양식 → 추출 결과가 즉시 이상함), LLM은 **조용히** 흔들린다(측정조차 어려움).

### 오탐 vs 누락 — "애매하면 넣어라"의 비용

처음엔 "애매하면 `rendered_text`에 넣어라"로 갔다. 근거는 "오탐은 사람이 지우면 되지만 누락은 아무도 못 잡는다"였다. **틀렸다.**

오탐은 사람이 지우는 게 아니라 **하류를 잘못된 방향으로 민다.** `90%`를 노출 문구로 넣으면 builder가 게이지 옆에 `90%` 텍스트를 억지로 찍는다. 파이프라인에선 오탐이 사람 손을 안 거치고 그대로 실행된다.

### 실행 보장 vs 유연성

프롬프트에 "grep -cF로 세라"를 박으면 결정성이 올라간다. 그러나 **실행 보장이 없다** — 산출물엔 점수만 남고, grep을 돌렸는지 `-F`를 붙였는지 흔적이 없다. eval을 못 믿는 이유가 바로 그건데 같은 구조를 반복하게 된다.

> **스크립트를 어차피 쓸 거면 프롬프트가 아니라 `.py`에 쓰는 게 낫다.** 같은 코드인데 실행이 보장되고, 로그가 남고, 재현되고, 다음에 `-F`를 빼먹지 않는다.

## 5. 틀렸던 것들 (실패 기록)

오늘 AI(나)가 네 번 제안했고 네 번 다 데이터가 죽였다. **매번 메커니즘을 먼저 제안하고 나중에 측정했다.**

| # | 주장 | 반증 |
|---|---|---|
| 1 | "design_refine이 원문을 훼손해서 점수가 낮다" | ch8c0716 원문 위반 **0건**. questions 38/38, dialogue 14/14. **eval 점수를 1차 증거로 삼은 오판** |
| 2 | "강조 표기가 있으면 노출 문구" | `**90%**`, `1~12(오전)` 과다 포함 **6건** |
| 3 | "서술형으로 끝나면 제작 지시" | `[확인하기]`, `[내 사진첩에 저장하기]`, `[3. 수리 이야기…]` **손실 3건**. 게다가 모델이 규칙을 일관 적용도 못 함 — `[시작하기]`(…버튼 배치)는 넣고 `[내 사진첩에 저장하기]`(…버튼 배치)는 뺌 |
| 4 | "typed slot이면 타입이 곧 의미라 판정 불필요" | `dialogue` 9~15로 반증. 혼합은 줄 **사이**가 아니라 줄 **안**에 있음 |

4번 보충 — 혼합이 줄 안에 있다는 것:

```
'화면 하단 중앙에 노란색의 커다란 [시작하기] 버튼 배치.'
 └─────────── 지시 ───────────┘ └ 노출 ┘ └ 지시 ┘
```

`kind=button` 라벨을 붙여도 줄 전체가 노출이 되진 않는다. **typed slot은 판정을 없애는 게 아니라 옮길 뿐이다.**

사용자의 반문이 매번 이걸 잡아냈다 — "스크립트는 input 양식에 의존적이지 않냐", "enum 닫으면 되는 거냐". **가설을 죽인 건 AI가 아니라 사람의 질문이었다.**

## 6. 통한 것

사용자가 제안한 프레이밍: **"원문을 존중하되 render할 것과 의도 지시를 나눠라."**

문법 휴리스틱을 전부 버리고 기준을 하나로 바꿨다 — **"학습자가 화면에서 이 문자열을 읽는가?"**

```
'화면 하단 중앙에 노란색의 커다란 [시작하기] 버튼 배치.'
 └────────── 의도 지시 ──────────┘ └ 렌더 ┘ └ 지시 ┘
 → rendered_text = ["[시작하기]"]
```

원문 서술은 `content`에 그대로 남으므로 지시를 잃지 않는다.

### 검증 — 반드시 2회 이상 돌릴 것

v1→v2 비교는 **오염됐었다.** elements가 58→101로 뛰었는데 규칙은 elements 개수와 무관했다. 즉 변화가 규칙 때문인지 드리프트인지 구분할 수 없었다. 그래서 같은 규칙으로 **두 번 독립 실행**했다.

| | probeA | probeB |
|---|---|---|
| `예:` 예시 누출 | **0건** | **0건** |
| v2가 잃던 라벨 3개 | **전부 포착** | **전부 포착** |
| v1이 넣던 과다 포함 6종 | **전부 없음** | **전부 없음** |
| 체크리스트 | 40 | 47 |
| 누락 | **2** | **2** |
| **content_fidelity** | **3점** | **3점** |

**1점 → 3점.** 남은 2건은 전부 진짜다(`[확인하기]` 대괄호 벗김 — 실제 위반, `[STEP 2. 수리로 해결해요]` — 노출 여부 미정).

그리고 **게이트가 만족 가능해졌다.** 예전엔 eval이 제작 지시를 세는 한 누락 0개가 원리적으로 불가능했다.

## 7. 오늘 적용한 변경

| 파일 | 변경 |
|---|---|
| `schemas/planner_output.schema.json` | `elements[]`에 `rendered_text: string[]` (required, `[]`=노출 없음 — Codex strict 제약상 optional 불가) |
| `prompts/planner_system.md` | "학습자가 읽는가" 기준 + 실패 사례를 뒤집은 예시 표 |
| `content_rubric.yaml` | `counting_rule` (d)를 `content` → `rendered_text` |
| `prompts/content_eval_system.md` | 체크리스트 교체, `grep -cF` 강제(`-F` 근거 명시), `input.json` 참조 제거 |
| `prompts/content_critique_system.md` | 체크리스트 교체 |
| `stages/content_evaluator.py` | `input.json` 입력 제거 — 경로만 든 껍데기였고 "storyboard를 보라"는 착각만 만듦 |
| `runner.py` | **content_refine 분기 독립** + `--content-eval-only`에 planner 검증 추가 |

분기 수정:

```python
# 이전: content_refine이 design PASS일 때만 닿는 3순위 → 10/10에서 0회
# 지금: 각 축이 자기 게이트에만 반응
if asset_change_needed:                          asset 재생성
if asset_change_needed or design_status != PASS: design_refine
if eval_status != PASS:                          content_refine
```

`run_asset_revision_stage`가 내부에서 `design_refine`을 부르던 것도 제거했다(안 그러면 한 iteration에 두 번 돈다). 순서는 design → content — content_refine이 CSS를 안 건드리는 보수적 stage라 마지막이 안전하다.

**비용**: 두 축이 다 REJECT면 iteration당 HTML 전체 재작성 2회 = 최악 80분.

## 8. 남은 것

- **`[STEP 2. 수리로 해결해요]`** — 화면 라벨인가 목적지 이름인가. 미결정.
- **척도 포화** — `4개 이상 = 1점`이라 6개든 7개든 같은 점수. 지금은 누락 2개라 안 걸리지만 구조는 남음.
- **stateless 판정** — eval이 이전 결과를 안 봄. `feedback_scaffolding`이 *거의 같은 서술로 3점과 1점*을 낸 문제는 `rendered_text`가 못 고침.
- **분기 수정이 아직 실행돼 본 적 없음** — content_refine이 실제로 도는지, design→content 순차가 서로를 안 지우는지는 full run으로 확인 필요.
- **부작용** — 기존 7/15 planner 2개가 schema REJECT(73·87 errors). 그 run들은 재개·재채점 불가.

## 9. 교훈

1. **eval 점수를 1차 증거로 쓰지 마라.** 산출물을 직접 대조하라. "점수가 낮으니 품질이 나쁘다"가 오늘 첫 오판이었고, 실제로는 채점자가 틀렸다.
2. **1회 실행으로 프롬프트 효과를 측정하지 마라.** 드리프트가 규칙 효과보다 클 수 있다. 최소 2회.
3. **메커니즘을 제안하기 전에 측정하라.** 오늘 4번 실패한 공통 원인이다.
4. **프롬프트의 지시와 데이터의 실제 모양이 어긋나면 LLM은 지시를 따른다.** 오탐이 "저작"될 수 있다. 모델을 의심하기 전에 지시를 읽어라.
5. **LLM에게 "무엇을 셀지" 정확히 주면, 세는 일은 도구로 시킬 수 있다.** 반대로 "무엇"이 흐리면 도구를 줘도 소용없다.
6. **안정성은 목적이 아니라 수단이다.** 40 vs 47로 흔들려도 점수가 같으면 문제없다.
7. **문서가 세어준 것은 안정적이다.** 상류 문서의 구조가 하류 LLM의 결정성을 정한다. 슬롯 설계로는 못 만든다.
8. **파이프라인에서 오탐은 사람이 안 거른다.** 그대로 실행돼 하류를 잘못된 방향으로 민다. "애매하면 넣어라"는 대화형에선 맞고 파이프라인에선 틀리다.
