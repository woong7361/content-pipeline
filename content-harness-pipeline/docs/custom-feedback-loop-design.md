# 커스텀 피드백 루프 설계

content-pipeline 산출물에 대한 사람의 교정 피드백을, 일회성으로 흘려보내지 않고
파이프라인 자체의 제약(prompt/schema/stage)으로 승격시키기 위한 루프 설계 문서다.

---

## 1. 개요

### 1.1 왜 피드백 루프가 필요한가 — 피드백이 그냥 지나쳐 간다

사람이 산출물을 보고 "이건 이렇게 하지 마"라고 교정해도, 그 피드백은 대부분 **그 순간의 대화에서만 소비되고 사라진다.**
문제는 파이프라인이 매 run마다 **자기가 만든 결함을 스스로 반복**한다는 것이다.

- 실제 사례: `runs/2026-07-08_ch802d08`에서 말풍선 위 요약 라벨(`📢 도서관 고장 알림`),
  전광판 asset 위 텍스트에 붙은 표면명 접두어(`전광판: …`)가 **iter_001~005 다섯 번의 개선 루프 내내 그대로 유지**됐다.
- 이유: 이 결함을 검사하는 축이 어느 리뷰 단계에도 없어서, 파이프라인 내부 루프로는 절대 잡히지 않았다.
  사람이 지적하지 않으면 다음 run에서도 똑같이 나온다.

즉 파이프라인의 자기개선 루프(review→refine)는 **자기가 볼 수 있는 축 안에서만** 돈다.
그 축 밖의 결함은 사람만 볼 수 있고, 그 사람 피드백을 구조로 남기지 않으면 매번 재발한다.
피드백 루프의 목적은 **사람만 볼 수 있는 결함을 파이프라인이 볼 수 있는 제약으로 옮기는 것**이다.

### 1.2 왜 설계가 필요한가 — proposal로 만들려다 두 벽에 부딪혔다

피드백을 곧바로 규칙(proposal)으로 승격시키려 했더니 두 가지 구조적 문제가 드러났다.

**(A) Target 문제 — 반영처가 틀렸다.**
기존 `피드백 → problem.md → rule 루프`는 rule을 **AGENTS.md**에 추가하도록 설계돼 있었다.
그러나 AGENTS.md는 *나(Claude Code, 오퍼레이터)*만 읽는다.
파이프라인 에이전트(builder·design_review·refine 등)는 `runner.py`가 AGENTS.md를 프롬프트에 주입하지 않으므로 **AGENTS.md를 보지 못한다.**
파이프라인 산출물의 결함을 고치려면 수정처는 반드시 `prompts/*_system.md`, `schemas/*.json`, `stages/*.py` 여야 한다.
AGENTS.md에 rule을 아무리 쌓아도 파이프라인 행동은 바뀌지 않고, 피드백은 여전히 흘러간다.

**(B) 비용 문제 — 매번 분석하면 비싸다.**
기존 루프는 "기록한 뒤에야 실제 수정 작업을 진행한다"고 해서, **피드백 한 건마다** 원인 추적을 강제했다.
그런데 어느 stage/prompt/schema가 원인인지 찾는 파이프라인 정독은 비싼 작업이다.
대부분의 피드백은 저빈도·일회성이라, 매번 전체를 정독하면 비용이 낭비되고,
근거가 얇은 상태에서 성급하게 구조를 바꿔 오반영할 위험도 커진다.

### 1.3 Trade-off

| 축 | 즉시 반영 | 지연 반영(축적 후) |
|---|---|---|
| 재발 | 빠르게 끊음 | 승격 전까지 같은 문제 몇 번 더 겪음 |
| 비용 | 매 건 분석 → 높음 | 임계치 도달분만 분석 → 낮음 |
| 오반영 | 근거 1건으로 성급한 구조 변경 위험 | 반복 확인 후 반영 → 안전 |

| 축 | 자동 승격 | 승인 게이트 |
|---|---|---|
| 사람 손 | 덜 감 | 개입 필요 |
| 통제 | 잘못된 구조 변경·비용 폭주 위험 | 비용·범위 예측 가능 |

**선택:** *지연 반영 + 승인 게이트.*
저빈도 피드백은 싸게 흘려적재하고, 동일 패턴이 반복 확인(임계치=3회)될 때만
사람 승인 하에 비싼 파이프라인 분석을 한다. 비용은 통제 가능한 지점에만 발생시킨다.

이 선택이 감수하는 비용: 어떤 결함은 규칙으로 승격되기 전까지 2~3회 더 재발한다.
이는 "매 건 분석"의 비용·오반영 위험과 맞바꾼 의도된 trade-off다.

## 2. 설계

### 2.1 핵심 원칙

1. **수정처 우선(target-first):** 피드백은 반영처에 따라 갈라진다.
   파이프라인 산출물 결함 → `prompts`/`schemas`/`stages`.
   나의 작업 습관·오퍼레이션 → `AGENTS.md`. 원장도 이 기준으로 분리한다.
2. **비용 게이트:** 값비싼 파이프라인 정독은 *승인을 받은 뒤에만* 한다.
   승인 전 단계에서는 파이프라인 구조를 열어보지 않는다.
3. **축적 후 승격:** 근거가 임계치만큼 쌓여야 구조 변경을 제안한다.

### 2.2 3단계 게이트

```
[1] 기록 (싸다 · 매 피드백)
      - 증상·category·근거만 원장에 적재
      - 원인은 "가설 1줄"까지만 (확정 분석 금지)
      - 금지: runner/prompts/schemas 구조 열람
      │
      │  동일 category 누적 3회 도달
      ▼
[2] 요청 게이트 (거의 무료)
      - 사용자에게 "이 category 3회 쌓임. 구조분석 승인?"만 질문
      - 여전히 파이프라인 구조 열람 금지
      │
      │  사용자 승인
      ▼
[3] 분석·반영 (비싸다 · 승인 후에만)
      - 그제서야 파이프라인 정독 → 원인 stage/prompt/schema 특정
      - 수정안 제시 → 사용자 승인 → prompts/schemas/stages 반영
      - 원장 상태를 '반영됨'으로 전환
```

**단계별 허용/금지**

| 단계 | 허용 | 금지 |
|---|---|---|
| [1] 기록 | 산출물 파일 1~2개 열람, 증상·근거 기록, 가설 1줄 | 파이프라인 구조(runner/prompts/schemas) 정독, 즉시 수정 |
| [2] 요청 | 누적 근거 요약, 승인 질문 | 구조 열람, 자동 반영 |
| [3] 반영 | 파이프라인 정독, 원인 특정, 수정안 제시·반영 | 승인 없는 반영, 수정처 오배정(AGENTS.md에 파이프라인 rule) |

### 2.3 원장 분리

| 원장 | 대상 | 수정처 | 승격 시 |
|---|---|---|---|
| `content-harness-pipeline/proposals.md` | content-pipeline 산출물(run output, 프롬프트/스키마/러너 동작) | `prompts/`·`schemas/`·`stages/` | 파이프라인 파일 수정 |
| 최상단 `problem.md` | `index.html`, 나의 작업 습관·오퍼레이션 | `AGENTS.md` | AGENTS.md rule 추가 |

기존 `problem.md`가 이 둘을 섞어 전부 AGENTS.md로 몰아넣던 것이 1.2(A)의 원인이었다.
파이프라인 관련 항목은 `proposals.md`로 이관한다.

### 2.4 `proposals.md` 포맷

문서 상단에 **요약표**(한눈에 얼마나·왜 쌓였는지), 그 아래 **항목**을 둔다.

**상단 요약표**

| category | 상태 | 발생횟수 | 최근일 | 수정처(가설) |
|---|---|---|---|---|
| redundant-surface-label-text | 분석대기 | 3 | 2026-07-09 | prompts/builder_system.md, prompts/design_review_system.md |

**항목 템플릿**

```markdown
### [category] 한 줄 요약

- 상태: 열림 | 분석대기 | 분석중 | 반영됨 | 보류
- 발생 횟수: N
- 최초/최근 발생일: YYYY-MM-DD / YYYY-MM-DD
- 증상(근거):
  - YYYY-MM-DD: <무엇이 잘못됐나> — <근거: 파일:라인 또는 스크린샷 경로>
- 원인 가설(1줄, 미확정): <어느 stage/prompt가 원인일 것 같은지 짧은 추정>
- 수정처 후보: prompts/... | schemas/... | stages/...
- 반영 메모: <[3]에서 확정한 원인 / 실제 수정 / 승인 여부>
```

### 2.5 상태 머신

```
열림 ──(동일 category 3회)──► 분석대기 ──(사용자 승인)──► 분석중 ──(반영·검증)──► 반영됨
                                   │
                                   └──(사용자 거절/보류)──► 보류   (발생횟수는 계속 누적)
```

- **열림:** 임계치 미만. 계속 싸게 적재만 한다.
- **분석대기:** 3회 도달해 [2] 요청을 던진 상태. 아직 구조 안 봄.
- **분석중:** 승인받아 [3] 진행 중.
- **반영됨:** 파이프라인 파일 수정 완료. 다음 run에서 재발 여부로 검증.
- **보류:** 사용자가 지금은 아니라고 함. 발생횟수는 유지되어 재승격 가능.

### 2.6 임계치

- 승격 트리거 = **동일 category 누적 3회.**
- 단일 피드백 안에 같은 성격의 사례가 여러 건이면 그 횟수만큼 카운트한다
  (예: 한 번의 지적에 3사례 → 즉시 분석대기).
- category는 중복 감지의 기준이다. 새 증상을 적기 전에 같은 대상·같은 성격의 기존 항목을 먼저 찾아 횟수를 갱신한다(중복 항목 신설 금지).

### 2.7 첫 적용 대상: `redundant-surface-label-text`

이번 피드백(에셋/대사로 이미 표현된 정보를 라벨·접두어로 중복)은 단일 피드백 3사례로 임계치를 채웠다.
→ `proposals.md`에 **분석대기** 상태로 이관하고, 실제 원인분석·프롬프트 수정은 [3]에서 사용자 승인 후 진행한다.
(사전 조사 결과 수정처 후보는 `prompts/builder_system.md`, `prompts/design_review_system.md`.)

---

## 3. 구현 항목 (이 설계 승인 후)

1. `content-harness-pipeline/proposals.md` 신설 (요약표 + 템플릿 + 상태머신 안내).
2. 최상단 `AGENTS.md`의 "피드백 → problem.md → rule 루프" 섹션을 3단계 게이트 + 원장 분리 구조로 교체.
3. 기존 `problem.md`의 파이프라인 관련 항목(`redundant-surface-label-text`,
   `asset-revision-refine-routing`)을 `proposals.md`로 이관, `problem.md`에는 index.html·오퍼레이션 항목만 남김.
