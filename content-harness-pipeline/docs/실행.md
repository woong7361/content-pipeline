# 실행

명령어는 `content-harness-pipeline` 디렉토리에서 실행한다.

```bash
cd content-harness-pipeline
python -m pip install -r ./requirement.txt
```

입력 스토리보드가 PDF라면 읽기 경로를 먼저 확인한다.

```bash
python -B -m stages.scripts.storyboard_readability "../스토리보드.pdf"
```

콘텐츠 제작형 파이프라인을 실행한다.

```bash
python -B ./produce_lesson.py "../스토리보드.pdf" --run-id g4l02 --gyo6-root {GYO6}
```

인터뷰 직전까지만 만든다.

```bash
python -B ./produce_lesson.py "../스토리보드.pdf" --run-id g4l02 --gyo6-root {GYO6} --through interview
```

인터뷰 답변을 반영해서 이어서 만든다.

```bash
python -B ./produce_lesson.py runs/g4l02 --gyo6-root {GYO6} --start-at interview_brief --interview-notes runs/g4l02/interview/answers.md
```

같은 run을 의도적으로 다시 만들 때만 `--overwrite`를 붙인다.

```bash
python -B ./produce_lesson.py "../스토리보드.pdf" --run-id g4l02 --gyo6-root {GYO6} --overwrite
```

초안 끝에서 **Typecast 웹 대본**을 내보내고 알림을 띄우며 멈춘다(인물 대표 그림이 있을 때).
`runs/g4l02/audio/web/script.md` 를 보고 인물별 `script-*.txt` 를 웹 편집기에 붙여 넣어 목소리를 골라 만든다.
내려받은 파일은 `runs/g4l02/audio/web-inbox/` 에 넣고 다시 돌린다(가져오기는 파일 형식 확인 뒤 만든다).

```bash
python -B ./voice_lesson.py runs/g4l02
```

Typecast API 는 쓰지 않는다(웹 요금제만 쓴다). `--no-voice` 로 건너뛴다.

이미 만든 초안을 LLM 없이 다시 검사한다.

```bash
python -B ./produce_lesson.py runs/g4l02 --gyo6-root {GYO6} --check-only
```

배치 전에 무엇을 옮길지만 확인한다.

```bash
python -B ./install_lesson.py runs/g4l02 --target {GYO6} --lesson 4-1/02 --dry-run
```

배치한다.

```bash
python -B ./install_lesson.py runs/g4l02 --target {GYO6} --lesson 4-1/02
```

이미 있는 차시를 덮을 때는 `--overwrite` 를 붙인다. 지난 배치 뒤 gyo6 쪽에서 고친 파일이 있으면
멈추고 목록을 보여 준다 — 그 수정이 맞으면 run 으로 먼저 가져오고, 버려도 될 때만
`--discard-target-changes` 를 붙인다. 배치 기록은 `runs/g4l02/install-record.json` 에 남는다.

gyo6_content 쪽에서 빌드한 뒤 **반드시** 화면 검증을 돌린다. `produce_lesson.py` 는 데이터만 보고 끝나므로
끝날 때 이 명령을 안내한다.

```bash
cd {GYO6} && npm run build:lesson -- 4-1/02
python -B ./verify_lesson.py runs/g4l02 --target {GYO6} --lesson 4-1/02
```

네 층을 싼 것부터 돈다 — ① 화면 결함(`check_rendered`) ② 기능 테스트(문항을 실제로 풀어 오답·힌트·정답 확인)
③ 전 화면 캡처 ④ 화면 판정·스토리보드 대조(LLM 2회). ①②에서 막는 것이 나오면 ④는 건너뛴다.
LLM 없이 ①~③만 보려면 `--skip-llm`.

결과는 `runs/g4l02/verify/report.md` 에 요약되고, 걸린 것은 고칠 수 있는 담당자별 파일로 나뉜다.

| 파일 | 담당 | 다음 |
|---|---|---|
| `to-developer.md` | 개발 단계 | `produce_lesson.py runs/g4l02 --gyo6-root {GYO6} --start-at senior_developer --through develop --screen-report runs/g4l02/verify/to-developer.md` |
| `to-asset.json` | 그림 단계 | `produce_lesson.py runs/g4l02 --gyo6-root {GYO6} --start-at asset_render --through render --rerender-from runs/g4l02/verify/to-asset.json` |
| `to-storyboard.md` | 원고 담당 | 원문 확인 → 인터뷰 답으로 반영 |
| `to-runtime.md` | gyo6 공통 런타임 | 그쪽 레포에 알린다 |
| `to-human.md` | 사람 | 담당을 정한다 |

고친 뒤에는 배치 → 빌드 → `verify_lesson.py` 를 다시 돈다.

예전 단축 경로가 필요하면 `build_lesson.py`를 직접 쓸 수 있지만, 기본 초안 경로는 `produce_lesson.py`다.

```bash
python -B ./build_lesson.py "../스토리보드.pdf" --run-id g4l02 --gyo6-root {GYO6}
```

문법만 빠르게 확인할 때:

```bash
python -B -c "from pathlib import Path; files=['produce_lesson.py','build_lesson.py','install_lesson.py','review_lesson.py','verify_lesson.py','validate.py']; [compile(Path(f).read_text(encoding='utf-8'), f, 'exec') for f in files]; print('syntax ok')"
python -B -m unittest tests.test_pipeline_foundations
```

## 장단점

장점:

- 실제 제작 조직처럼 기획, 와이어프레임, 인터뷰, 비주얼 설계, 개발 판단이 분리되어 결정 근거가 남는다.
- 인터뷰 답변이 `planning/production-guide.md`로 굳어져 뒤 stage가 같은 지침을 읽는다.
- 개발 stage가 `gyo6_content` 원자, hook, layout 참조를 보고 만들기 때문에 이식 실패를 줄인다.
- `pipeline-log.jsonl`, `review/design-review-log.md`, `lesson/page-map.md`가 남아 나중에 어디서 결정이 바뀌었는지 추적하기 쉽다.

단점:

- LLM 호출이 5회로 늘어 단축 경로보다 느리고 비싸다.
- md 중간 산출물이 많아져, 사람이 중간 파일을 고치면 어느 파일이 최신 지침인지 관리해야 한다.
- 인터뷰 답변이 늦게 들어오면 이후 디자인과 개발을 다시 돌려야 할 수 있다.
- 이미지 파일 생성은 실행 환경의 이미지 생성 도구가 연결되어야 완전 자동화된다. 연결이 없으면 `asset-plan.md`에 프롬프트와 파일 계획만 남긴다.
